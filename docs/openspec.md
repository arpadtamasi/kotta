# Kotta and OpenSpec

Kotta does not need OpenSpec. A change is Kotta's own — `.kotta/changes/<name>/`, a proposal in
prose and a model delta beside it — and the technical model is the only specification a project
must keep. OpenSpec is an optional companion, in three ways: an existing OpenSpec repository comes in
through `kotta import openspec`; a project may keep OpenSpec's capability specs beside the model,
generated from it or written by people (`narrative:` in `.kotta/config.yaml`); and changes an
earlier release kept under `openspec/changes/` move into the workspace with `kotta migrate`.

## When OpenSpec alone is enough, and when to add Kotta

**OpenSpec alone is enough** when the change is small, you work alone, the requirements and their
scenarios say everything the code needs, and nobody will ask later why a rule is the way it is. The
operator ran a project on plain OpenSpec for a week and did not miss Kotta. Writing a delta as
nodes took 2.3 times as long as writing it in prose.

**Add Kotta** when the product has rules, states and interfaces that must survive many changes:

- you need the goals, actors and reasons kept, not just the requirements (prose left all 11 goals
  and 14 stories of one measured spec unsaid);
- an agent translates or fills in, and you need to see which decisions it made alone;
- lifecycles matter: a state machine's removed or reversed transition is a conflict `plan` names;
- several modules or repositories rely on one another's promises;
- you want the code to say which promise it keeps, and a report of which ones nothing keeps.

The measurements are in [Concepts](concepts.md).

## How they fit

| | OpenSpec | Kotta |
| --- | --- | --- |
| A change | `openspec/changes/<name>/` | `.kotta/changes/<name>/`: `proposal.md`, `conversation.md`, `model/`, `planning.md`, `approval.yaml` |
| The accepted state | `openspec/specs/<capability>/spec.md` | `.kotta/spec/<form-directory>/*.md` |
| Landing a change | OpenSpec's archive | `kotta archive`: merges the model, regenerates `openspec/specs/` where a generated narrative is kept, moves the change to `.kotta/changes/archive/` |

In a Kotta project every proposal starts with `kotta change new <name>`, whether or not the project
uses OpenSpec. Kotta writes nothing under `openspec/changes/` and reads no change there: a change
left there is reported (`CHANGE_STRANDED`) until it is moved. See
[The planning phase](planning-phase.md#opening-a-change).

## Keeping an OpenSpec narrative

`narrative:` in `.kotta/config.yaml` (or `openspec/config.yaml`) decides whether OpenSpec's
capability specs are kept beside the model, and who writes them:

| Value | What Kotta does with `openspec/specs/` |
| --- | --- |
| `none` (default) | nothing: it is neither written nor checked, and `plan` reports no drift |
| `generated` | `archive` regenerates every capability a change touches from the model |
| `authored` | people write it; `plan` and `archive` report where a bound requirement disagrees with its node |

Only with `generated` or `authored` does an obligation carry OpenSpec's keyword, SHALL or MUST; with
`none` it is written plainly, in the project's language. `kotta validate` warns `NARRATIVE_UNSET`
when `openspec/specs/` holds specs and nothing sets the key: before 1.0.0-alpha.3 that meant
`generated`, and now it means `none`. See [Configuration](configuration.md).

## The binding: `<!-- kotta: ID -->`

With `generated` or `authored`, every entry `archive` generates — Purpose, requirement, scenario, use case, story — carries the id
of the node it came from in a `<!-- kotta: ID -->` line under its heading. On a requirement, that line
is a binding Kotta checks:

```markdown
### Requirement: A kijátszott kézlapok összege legfeljebb 13
<!-- kotta: BR-01m37bp2vs8vdrgmdbsrq1g8vx -->
Egy akcióban egy, kettő vagy három kézlap játszható ki együtt, de az összértékük kivétel nélkül
legfeljebb 13 lehet. …
```

`kotta plan` and `kotta archive` compare every bound requirement's statement (its text up to the
first bold sub-heading) with the node's first required section. They agree when the two are the
same, whitespace aside, or when the requirement still carries the sentence the node's provenance
quotes. A disagreement is reported with both texts and both places; neither side is rewritten.

## Generated specs and `openspec validate --specs --strict`

With `narrative: generated` every spec `archive` writes starts with:

```markdown
<!-- Generated by `kotta archive` from the technical model. The model is the accepted truth: change the nodes, not this file. -->
```

The generator carries the nodes' text as written and invents nothing, so what OpenSpec's strict
validation checks has to be in the model:

- **SHALL or MUST** in every obligation: a rule's Rule, an interface's Postconditions or
  Invariants, a quality attribute's Response. With an OpenSpec narrative kept, `kotta validate` and
  `kotta plan` enforce it on a change's nodes, and `kotta spec new` lays a hint into those sections.
- **A scenario** for every requirement: an example whose `subjects` name it. An interface with no
  example gets its own contract as the scenario. Otherwise `archive` warns `NARRATIVE_NO_SCENARIO`.
- **A Purpose** of at least 50 characters: a goal node naming the capability. Otherwise `archive`
  warns `NARRATIVE_PURPOSE_BRIEF`.

The casino repository shows what happens without them. Its rules were written in Hungarian before
the keyword check existed, and its specs were generated during the alpha, when use cases and
stories still became requirements. `openspec validate --specs --strict` there fails all five specs:
OpenSpec warns that a requirement "should contain SHALL or MUST", which strict mode does not allow,
and some requirements have no scenario.

To write `openspec/specs/` by hand instead, set `narrative: authored` in `.kotta/config.yaml` (or in
`openspec/config.yaml`). `archive` then writes no narrative and reports each bound requirement's
drift as a warning.

## Importing an existing OpenSpec repository

```bash
kotta import openspec [--change <name>]
```

reads `openspec/specs/<capability>/spec.md` and opens a new change under `.kotta/changes/` (by
default `import-openspec-<date>`; an existing directory is refused). OpenSpec is the source, never
the change's home: nothing under `openspec/` is written. Into its `model/` it drafts exactly what
the prose states, copied, never written:

| From | Drafted as |
| --- | --- |
| each `### Requirement:` | a business rule; its text is the Rule |
| each `#### Scenario:` | an example proving that rule, its steps as Given / When / Then |
| each capability's `## Purpose` | a goal; the Purpose is its Outcome |

Every draft is `level: stated`, `decided_by: agent-decided`, its source naming the requirement it
came from: nothing is accepted until a human says yes at the gate. A section the prose has nothing
for holds `<!-- kotta import: not derivable from the narrative spec; the planning phase asks for it. -->`
and still counts as empty. A requirement bound to an accepted node, or titled exactly like one
accepted node of its kind, changes that node under its own id instead of duplicating it.

The import drafts no actor, use case, entity or state machine. Its `proposal.md` lists OpenSpec's
archived changes (`openspec/changes/archive/`) as history for the rationale, and says what comes
next: run the `plan-change` skill to derive the rest and ask where no source says, then
`kotta plan <change>` and the gate. The narrative itself is only read. When no config sets
`narrative:`, the import also says that after it the model is the only specification and archive
leaves `openspec/specs/` alone, and asks whether to keep it as `generated` or `authored`.

```text
Imported 1 capabilities (1 requirements, 1 scenarios) into the change import-demo: 1 rule, 1 example and 1 goal drafts under .kotta/changes/import-demo/model/, all agent-decided.
…
Not drafted: actor, use-case, entity, state-machine — the planning phase derives them. The narrative was only read.
```

## Moving changes out of `openspec/changes/`

Up to 1.0.0-alpha.2 a Kotta change lived at `openspec/changes/<name>/`. `kotta migrate` carries it into the workspace (`--dry-run` shows the plan first):

- every open change under `openspec/changes/` moves to `.kotta/changes/<name>/` — in a Kotta
  project an OpenSpec proposal waiting there is a Kotta change too;
- an archived change that carries a Kotta `model/`, `planning.md` or `approval.yaml` moves to
  `.kotta/changes/archive/`; OpenSpec's own archive — proposals without a model — stays where it is,
  as the history `import` reads;
- in a moved change that is not approved, provenance sources naming `openspec/changes/<name>/` are
  rewritten to `.kotta/changes/<name>/`. An approved change moves byte-identical, since its receipt
  is a hash of its model, and the report notes that its sources still name the old folder;
- where `openspec/specs/` holds specs and nothing sets `narrative:`, it writes `narrative: generated`,
  so archive keeps doing what it did.

Nothing under `.kotta/spec/` is read or written. A target that already exists stops the migration
before anything is written, and a second run says there is nothing to migrate. To move one change
by hand, `kotta change list` prints the `git mv`. The board still serves Markdown under `openspec/` for
provenance written before the move.
