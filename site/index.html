Prose alone loses what the code needs.

A narrative spec is where a change is argued. It is not where the agreement survives. Measured on real projects, prose keeps losing the same four things.

The why goes unsaid.The what and the how are written down; the goals and the stories — why, and for whom — are not.
Structure does not come back.Round-trip a model through prose and the goals it served are lost, and invented ones take their place.
Copied promises drift.The same interface, copied into two repositories, already says two different things.
The machine decides unnoticed.Wherever a gap is filled in silently, an agent made a product decision nobody saw.

Three ways in.

The narrative says what a change is for. The model says precisely what was accepted. The code keeps it and says so. Wherever you start, you arrive at the same model.

  1. A new product

    OpenSpec change → /plan-change → model

    Write the change in prose, the way you already do. The planning skill translates it into model nodes, marks where each one came from, and asks for what nobody said instead of inventing it.

  2. An OpenSpec repository

    kotta import openspec → kotta plan

    The requirements, scenarios and purposes you already have become a first model, every node marked as the machine’s draft. The planning report lists what the prose never said.

  3. A Kotta 0.x workspace

    kotta migrate --dry-run → kotta migrate

    The specification stays byte for byte as it is. The old process state moves into a read-only archive, and no identifier is lost on the way.

One change, one human yes.

The narrative proposes, the model is measured, the human decides once, and the rest is mechanical. Nothing asks again after the gate.

  1. 01

    Propose

    Argue the change in prose, then translate it into model nodes, each with its provenance.

    /plan-change
  2. 02

    Plan

    Measure the delta against the accepted model: conflicts, open questions, drift, what the machine decided.

    kotta plan <change>
  3. 03

    Approve

    The one human gate. You say yes in the chat; Kotta records the receipt.

    kotta approve <change> --by you
  4. 04

    Archive

    The model is merged, the narrative is regenerated from it, and any drift is reported.

    kotta archive <change>

Not another spec tool. The layer between prose and code.

Keep the tools you already use. OpenSpec holds the narrative; Kotta holds the model it is measured against. They are partners, not rivals.

Install it. Plan one real change.

Kotta runs inside the repository you already have. Node.js 20+ and Git are the only runtime requirements. This is a pre-release, published under the next tag.

  • No service to deploy
  • No database to maintain
  • No account to create
  • No hidden state to trust
terminalverified setup
# Install the CLI
npm install --global @arpadtamasi/kotta@1.0.0-alpha.1

# Inside an existing Git repository:
# the form registry, the skills and the rules your agents read
kotta init

# From the chat: translate an OpenSpec change into the model
/plan-change

# Then measure it, say yes, and land it
kotta plan <change>
kotta approve <change> --by you
kotta archive <change>
