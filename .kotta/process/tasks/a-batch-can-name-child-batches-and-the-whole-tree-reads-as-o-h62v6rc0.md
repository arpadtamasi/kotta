# T-01kztxxfjpaxyam0g2h62v6rc0 — A batch can name child batches, and the whole tree reads as one work list

## Outcome

A batch can name other batches as members, so a large product's modules and workstreams have a level
above the contract without flattening. The nesting is grouping only: reading a parent yields both its
shape and the single ordered list of contracts underneath it, which is what lets an operator say
"run the whole big one" in chat and have the agent work out the rest.

## Measured problem

Reported on 2026-08-12: *"A Kotta jelenlegi modellje nem támogat egymásba ágyazott batch-eket.
Nagyobb terméknél jó lenne."* (`F-01kztt37st3xy3dmfnr23getrn`)

The model is flat by construction. `schemas/batch.schema.json` types `contracts` as an array whose
items must be contract ids, with `minItems: 1`, and there is no member of any other kind. A contract
carries a single `batch` string and `updateContainingBatch` is named for that assumption. The tree
has exactly two levels, so a product with modules, milestones and workstreams must flatten all of
them into one batch of many contracts or many unrelated batches with nothing above them.

`D-01kztxvppd40r77cq7kw9b8wzr` settles what nesting means here, and rules out the expensive half: a
child batch is **grouping**, not an execution unit. It has no coordinator branch, no `execution`
block of its own and no merge target, so the questions that would otherwise have to be answered —
what a child coordinator merges into, whether parallelism is per level or shared, what a
half-finished child means for the parent — do not arise.

The operator also said what the grouping is for: *"chatben mondhassam, hogy csinálja végig a nagyot,
majd a chat ai-ja megoldja a többit."* That is the load-bearing requirement. An agent cannot carry
out what it cannot enumerate, so the reading surfaces are not decoration here — they are the feature.

## Actors

- **Human.** Composes the tree, and asks in chat for a whole parent to be carried out. The approvals
  that gate signing and closing each contract are unchanged.
- **Calling agent.** Reads a parent, flattens it to an ordered contract list, and executes those
  contracts the way it executes any batch's members.
- **Kotta.** Records membership, refuses a shape that is not a tree, and answers both questions about
  a parent: what is under it, and in what order.

## Initial state

A workspace of batches and contracts in today's flat shape: every batch names contracts only, and
every contract belongs to at most one batch. No existing batch has a parent.

## States

Of a batch, unchanged in name and meaning: `backlog`, `defined`, `active`, `done`. Nesting adds a
position rather than a state:

- **root** — no parent. Every batch today.
- **child** — named by exactly one parent.

And a derived readable property, not stored:

- **leaf** — names contracts and no child batches. The only shape `batch start` ever runs.

## Transitions

- **root → child** via `kotta batch add <parent> <child-batch-id>`, the same command that adds a
  contract, routed by the kind of id it is given.
- **child → root** via `kotta batch remove <parent> <child-batch-id>`. Removing a child never
  touches the child's own members.
- **Batch lifecycle transitions** are unchanged for both. A child is signed, started and closed as
  the batch it already was.
- **`* → done` for a parent** now requires every child batch to be `done` as well as every directly
  named contract. This extends the existing rule rather than replacing it.

## Triggers

- A product is large enough that its batches want a name above them.
- An operator asks in chat for a whole parent to be carried out.

## Permissions

- Composing the tree needs no approval: membership is a statement about organisation, not about work.
  `batch add` and `batch remove` keep the gates they have today.
- Closing a parent keeps the human approval that `batch close` already requires, and now names any
  unfinished child the way it already names unfinished contracts.
- Nothing about nesting lets a contract be signed, started or closed without its own human decision.
  "Run the whole big one" is a request to do many gated things, not a way around the gates.

## Error paths

- **A child that would create a cycle**, directly or through any depth. Refused, naming the path that
  closes the loop.
- **A child that already has a different parent.** Refused, naming the current parent. One parent is
  the invariant that makes flattening well defined.
- **A batch added to itself.** Refused as the shortest cycle, with the same message shape.
- **A named child that does not exist.** Refused, as an unknown contract id already is.
- **`batch start` on a parent that has child batches.** Refused, naming the leaf batches it contains.
  Execution is a leaf operation, and pretending otherwise would invent the coordinator semantics this
  contract exists to avoid.
- **Closing a parent with an unfinished child.** Refused, naming the child, exactly as an unfinished
  contract is named today.

## Cancellation path

Nesting is undone by `batch remove`, which is one command and loses nothing: the child keeps its
members, its state and its history, and becomes a root again. There is no cascade — removing a parent
from the workspace never retires what it grouped, and `batch close` on a parent closes the parent
only.

## Retry and duplicate-action behaviour

- Adding a child that is already a member is a no-op and says so, as adding a contract already is.
- Removing a child that is not a member is a no-op and says so.
- Reading a tree is a pure read and repeats freely; a flattened list is derived on each read rather
  than stored, so it cannot fall out of date with the membership it describes.

## Audit and notification expectations

- `kotta batch show <id>` prints the tree beneath a parent and, separately, the flattened contract
  list in the order an agent should walk it: dependencies first, then declaration order.
- `kotta batch status <id>` reports a parent's progress over the whole subtree — how many of its
  contracts are done, and which child batches are still open.
- The board shows a parent's children next to its contracts, so the same shape reads there.
- No new lifecycle event. Membership is recorded in the batch file, which is where the reader looks.

## Scope

1. `schemas/batch.schema.json`: an optional `batches` array of batch ids on a batch, and `contracts`
   relaxed from `minItems: 1` so a parent may group children without naming contracts directly.
2. `validateBatch` (`src/commands/batch.ts`): children exist, no batch is its own ancestor, and no
   batch is named by two parents.
3. `updateBatchContracts` accepts a batch id and routes it to the `batches` array, keeping one
   command — `batch add` / `batch remove` — for both member kinds. Rename it if the name stops
   describing it.
4. A flattening read used by every surface: the ordered contract list under a batch, dependencies
   first then declaration order, computed and not stored.
5. `closeBatch` requires every descendant batch to be `done` alongside the directly named contracts,
   and names the first unfinished one.
6. `startBatch` refuses a parent that has children, naming the leaf batches inside it.
7. `batch show` and `batch status` print the tree and the flattened list; the board renders children
   beside contracts in the batch drawer (`ui/src/App.tsx`, where `batch.contracts` is already read).
8. `kotta validate` reports a cycle or a second parent as a workspace-level issue, the way it already
   reports a dangling member.
9. Documentation: `templates/AGENTS.md` and `README.md` say that nesting is grouping, that execution
   is a leaf operation, and that a whole parent is carried out by asking in chat.
10. Tests for every transition, refusal and reading above.

## Non-goals

- Any execution semantics for a child batch: no coordinator branch, no `execution` block, no merge
  target, no per-level parallelism. `D-01kztxvppd40r77cq7kw9b8wzr` rules these out, and adding them
  later is a separate decision, not an omission here.
- A command that runs a whole parent. The operator asks in chat and the agent walks the flattened
  list; a `batch execute --recursive` would be a second execution model beside the one that exists.
- Changing what a contract belongs to. One contract, at most one batch, and that batch is the leaf.
- Giving `authority.create_subcontracts` a meaning. It is still a permission for something the graph
  does not express, and this contract does not make it one.
- Migrating existing batches. Every batch today is a root, which is a valid tree.
- Depth limits. A tree that is too deep to read is the operator's problem to arrange, not a rule to
  enforce.

## Acceptance

- `kotta batch add <parent> <child-batch-id>` records the child, and `kotta batch show <parent>`
  prints both the child and the contracts underneath it.
- `kotta batch show <parent>` prints a flattened contract list covering every descendant, with
  dependencies before the contracts that declare them.
- `kotta batch status <parent>` counts progress across the whole subtree and names open children.
- Adding a child that would create a cycle of any depth is refused, naming the path.
- Adding a child that already has another parent is refused, naming that parent.
- `kotta batch start` on a parent with children is refused, naming the leaf batches.
- `kotta batch close --approve` on a parent with an unfinished child is refused, naming the child;
  with every child done and every direct contract done, it succeeds.
- `kotta batch remove <parent> <child>` returns the child to a root with its members intact.
- `kotta validate` reports a hand-made cycle or a doubly-parented batch.
- The board shows a parent's children beside its contracts.
- Every existing batch continues to validate, list, start and close unchanged.
- `kotta validate`, `npm run typecheck`, `npm run build` and the full suite pass.

## Verification

- `npx vitest run tests/integration/batch.test.ts` extended: compose a two-level tree, read it,
  flatten it, and close it; then each refusal — cycle at depth one and depth two, second parent,
  self-parent, start on a parent, close with an open child.
- A test asserting the flattened order puts a dependency before its dependent across two different
  child batches, so the ordering is a property of the tree and not of one batch.
- A test asserting a batch removed from its parent keeps its own contracts and state.
- A test asserting today's flat batches behave identically — the existing batch suite passing
  unchanged is the evidence.
- A board test asserting a parent renders its children.
- `npx vitest run --exclude '.worktrees/**'` — the full suite.
- `npm run typecheck` and `npm run build`.

## Constraints

- Nesting is grouping. No behaviour in this contract may depend on a child batch having its own
  branch, worktree or execution.
- The shape stays a tree: one parent, no cycles, at any depth.
- The flattened list is derived on read. A stored copy would be a second source of truth for
  membership, which `.kotta/` already answers.
- Human gates are untouched. A parent is a name, and naming work does not approve it.
- Existing flat batches keep their present behaviour and their present messages.

## Open decisions

None.

## Execution notes

- `D-01kztxvppd40r77cq7kw9b8wzr` is the product intent; read it before choosing any mechanism, since
  most of the design work here was deciding what *not* to build.
- `updateBatchContracts` (`src/commands/batch.ts:102`), `closeBatch` (`:339`) and `batchStatus`
  (`:306`) are the three functions that already walk `data.contracts`; each needs the subtree rather
  than a second traversal written next to it. One flattening helper, used by all three.
- The board already reads `batch.contracts` in `ui/src/App.tsx` — the closable, active-batch and
  dangling-member computations at lines 193, 197 and 238 each assume contracts only, and a parent
  with no direct contracts must not read as empty or dangling there.
- `schemas/batch.schema.json` requires `contracts` with `minItems: 1`. A parent that groups only
  children has none, so relaxing it is load-bearing rather than tidying.
- `F-01kztt37st3xy3dmfnr23getrn` is the observation behind this; disposition it against this contract
  rather than resolving it separately.

### Deviations

None in scope or behaviour. Two notes on how, both inside what the contract asked for.

The contract's scope item 3 said to rename updateBatchContracts if the name stopped describing it. It was kept: the exported name is still the one every caller and test uses, and the routing is a private helper beside it, so the rename would have been churn across the CLI and tests for no reader's benefit. Say so plainly rather than leave it looking overlooked.

Scope item 4 asked for a flattening read "used by every surface". closeBatch and batchStatus use subtreeContracts directly rather than flattenBatch, because they need the set and not the ordering; flattenBatch is the ordered read, used by validateBatch and available to any caller that wants the work list. Both sit on the same batchTree walk, so there is still one traversal, not two.

None. Everything found was inside the contract's scope.

### Known concerns

batch sign still validates and gates on the subtree through validateBatch, but its "every currently executable contract must be signed" check reads the parent's direct contracts only. For a parent that groups children this is vacuous rather than wrong — a parent is never started — but it means signing a parent does not assert anything about the contracts inside its children. The leaves are signed on their own, which is where that check does run.

The run view (ui/src/App.tsx, the active-batch progress cards) still counts batch.contracts directly rather than the subtree. It only ever renders active batches, and a parent cannot be started, so no parent reaches it today; if batch start ever gains a parent path that display would need the same helper.

Ordering between the two member kinds is fixed: direct contracts first, then children in declaration order, before dependency ordering rearranges them. Nothing lets an operator interleave a child batch between two direct contracts. Dependencies express the ordering that matters, so this has not been made configurable.
