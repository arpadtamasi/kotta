# T-015 — Manage coordinator branches through the complete package lifecycle

## Outcome

The package workflow owns and exposes the coordinator branch lifecycle from package start through post-merge cleanup. Starting a package creates or safely resumes its recorded coordinator branch, package completion preserves the branch for integration, and an explicit post-integration finalization returns the checkout to an up-to-date configured base branch and removes the merged local coordinator branch. The operator is never silently left doing new work on a coordinator branch for a completed, merged package.

## Actual behaviour

`a-team package start` requires the operator to already be on a non-protected branch but neither creates nor records a coordinator branch. When the final ticket closes, the package becomes done and ticket branches and worktrees are cleaned, but the main checkout remains on the coordinator branch. Even after that branch is merged remotely, the local checkout can remain on the completed package branch while the local base branch is stale. New package and finding work can then accumulate on the old coordinator branch without a warning.

## Expected behaviour

The CLI manages a coordinator branch as explicit package state. Package start can create or resume the branch from the configured base, status shows its lifecycle and whether cleanup is pending, and post-integration finalization performs only verified, fast-forward-safe cleanup. Dirty worktrees, unmerged coordinator work, divergent base branches, active claims, or attached ticket worktrees stop cleanup with actionable recovery guidance and without changing files, refs, or history.

## Reproduction steps

1. Start and execute a package from a manually created `coord/<package-id>` branch.
2. Close its final ticket so the package reaches `done`.
3. Merge the coordinator branch into the configured remote base branch.
4. Return to the original checkout and run `git branch --show-current`.
5. Observe that it still reports the merged `coord/<package-id>` branch and that subsequent A-Team mutations are recorded there.

## Environment

Observed on 2026-07-23 in the A-Team repository after P-002 was completed and merged through PR #15. The checkout remained on `coord/P-002`; `origin/main` contained the merge while local `main` was behind, and new P-003 workspace changes had accumulated in the checkout.

## Frequency

Deterministic for the current manual coordinator-branch workflow: completing and merging a package does not transition the original checkout back to the configured base branch.

## Impact

Branch provenance becomes misleading, unrelated package administration can be mixed into an already merged branch, and later commits or pull requests can contain accidental cross-package state. Because A-Team coordinates multiple agents, ambiguous branch ownership can also cause unsafe cleanup or conflicting work.

## Regression-test expectation

Add end-to-end Git fixture coverage for branch creation, safe resume, final-ticket completion, integration detection, cleanup success and every refusal path. Tests must prove that no refusal changes the checkout, working tree, local refs, or remote refs.

## Actors

- Operator coordinating a package.
- Agents executing package tickets in isolated worktrees.
- A-Team CLI managing package metadata, claims, branches, and worktrees.
- Git local repository and configured remote.
- Pull-request or integration workflow merging the coordinator branch into the base branch.

## Initial state

The repository is initialized for A-Team, `git.base_branch` identifies the protected base branch, and the package is either backlog/ready with no coordinator branch yet, active with recorded coordinator metadata, or done and awaiting verified integration cleanup.

## States

- `unstarted`: no coordinator branch is recorded.
- `active`: the package records its coordinator branch, base branch, and starting base commit.
- `done-unintegrated`: all package work is committed on the coordinator branch but merge into the configured base is not proven.
- `cleanup-pending`: integration is proven, but the coordinator checkout or local branch still exists.
- `cleaned`: checkout is on the updated base and the merged local coordinator branch is absent.
- `blocked-dirty`: cleanup is refused because tracked or untracked changes would be affected.
- `blocked-diverged`: cleanup is refused because the local base cannot be fast-forwarded safely.
- `blocked-in-use`: cleanup is refused because claims or linked worktrees remain.

## Transitions

- Starting an unstarted package from a clean configured base creates and checks out `coord/<package-id>`, then records the coordinator branch, base branch, and base commit atomically with package activation.
- Starting again on the recorded coordinator branch resumes idempotently.
- Starting from any other branch refuses with guidance; it does not invent or overwrite coordinator metadata.
- Closing the final ticket commits the done package state on the coordinator branch and moves the package to `done-unintegrated`; it does not delete the branch or switch away before integration.
- Status moves a done package to the observable `cleanup-pending` condition once ancestry proves the coordinator head is integrated into the configured base or its configured remote-tracking branch.
- An explicit post-integration package finalization command verifies every precondition, switches to the configured base, updates it by fast-forward only when needed, and deletes only the proven-merged local coordinator branch.
- Re-running finalization after successful cleanup is a successful no-op with a clear result.
- Any failed precondition leaves repository and canonical A-Team state unchanged.

## Triggers

Package start, package status inspection, final ticket closure, external integration of the coordinator branch, explicit post-integration finalization, cancellation, and retry.

## Permissions

The CLI may create and switch local branches, write package metadata through canonical writers, fast-forward the configured local base branch, and delete a local coordinator branch only after merge proof. It must not force checkout, reset commits, rewrite history, discard worktree changes, delete unmerged branches, delete remote branches, merge a pull request, or modify protected-branch history.

## Error paths

- A dirty or untracked working tree blocks branch creation, switching, base update, and cleanup when any step could affect those changes.
- A missing or invalid configured base branch blocks start and finalization.
- A stale local base may be fast-forwarded only when its configured remote-tracking ref is available and ancestry proves the update is fast-forward-only.
- A divergent local base blocks finalization and reports both refs and the manual recovery required.
- An unmerged or ambiguously merged coordinator branch is preserved.
- Active claims, linked ticket worktrees, or another worktree holding either target branch block finalization.
- A coordinator branch mismatch between metadata and the current branch blocks mutation.
- Partial Git failures return actionable diagnostics and preserve the branch unless every delete precondition was already proven.

## Cancellation path

Cancellation before a Git mutation leaves state unchanged. If cancellation or failure occurs after switching to the base but before local coordinator deletion, the command reports the exact completed transition and is safe to retry. No cancellation path discards changes or deletes a remote ref.

## Retry and duplicate-action behaviour

Package start on the already recorded coordinator branch is idempotent. Finalization recomputes ancestry and worktree preconditions on every run. A retry after switching but before deletion completes only the remaining verified cleanup. A retry after cleanup returns success without recreating or deleting anything. Concurrent attempts use the existing workspace locking discipline and one attempt must observe the other's completed state rather than racing branch deletion.

## Audit and notification expectations

Package metadata records the coordinator branch, configured base branch, and starting base commit. Human and JSON status expose current branch, integration evidence, and whether cleanup is pending or blocked. Start and finalization output list branch actions actually taken and skipped. No external notification or automatic remote deletion occurs.

## Scope

- Add canonical package metadata for coordinator branch, base branch, and starting base commit.
- Make package start create or resume the recorded `coord/<package-id>` branch under safe preconditions.
- Preserve the coordinator branch after the package becomes done so its final canonical commit can be integrated.
- Add an explicit post-integration package finalization or cleanup command.
- Verify integration by Git ancestry against the configured base or its configured remote-tracking ref.
- Switch back to the configured base, update it by fast-forward only, and delete only the verified merged local coordinator branch.
- Surface coordinator lifecycle and cleanup-pending state in CLI status and the local UI.
- Support legacy completed packages conservatively when exact branch naming and Git ancestry provide unambiguous evidence.
- Add unit, integration, CLI-contract, and legacy-migration tests plus operator documentation.

## Non-goals

- Automatically merging pull requests or pushing branches.
- Automatically deleting remote coordinator branches.
- Force-updating, resetting, rebasing, or resolving divergence on the base branch.
- Moving, stashing, committing, or discarding a dirty working tree on the operator's behalf.
- General-purpose Git branch management outside A-Team package coordinator branches.
- Cleaning ticket branches or worktrees beyond the existing ticket lifecycle contract.

## Acceptance

- Starting a package from a clean configured base creates and checks out its deterministic coordinator branch and records coordinator branch, base branch, and base commit.
- Repeating start on the recorded coordinator branch is safe and idempotent; starting from an unrelated branch is refused without mutation.
- Closing the final ticket leaves the complete coordinator branch available for pull-request integration and reports that post-integration cleanup remains.
- Package status and the UI distinguish active, done-unintegrated, cleanup-pending, blocked cleanup, and cleaned conditions without falsely changing the package's canonical completion status.
- Finalization refuses an unmerged coordinator branch and leaves the checkout and refs unchanged.
- Finalization refuses a dirty worktree, active claims, linked worktrees, a branch held by another worktree, and a divergent local base without losing data.
- For a proven merged coordinator branch and clean repository, finalization switches to the configured base, fast-forwards it if necessary, and deletes the merged local coordinator branch.
- Finalization never uses force operations and never deletes a remote branch.
- Re-running finalization after success is a documented successful no-op.
- A legacy completed package with no coordinator metadata is recoverable only when the exact conventional branch and ancestry proof are unambiguous; otherwise the command stops with manual guidance.
- Human and JSON output expose the evidence and actions used for every success or refusal.

## Verification

- Unit-test coordinator branch naming, protected-base detection, ancestry classification, cleanup-state derivation, and legacy inference.
- Use temporary Git repositories with bare remotes to test clean base start, recorded resume, unrelated-branch refusal, final-ticket completion, remote integration, stale local base fast-forward, and successful local deletion.
- Test dirty tracked files, untracked files, unmerged commits, divergent local base, missing remote tracking, active claims, linked worktrees, and branches checked out elsewhere; snapshot refs and status before and after every refusal.
- Test interruption after the base switch and prove a retry completes safely.
- Test concurrent duplicate finalization under the workspace lock.
- Verify CLI human and JSON contracts and UI presentation for every coordinator lifecycle state.
- Run typecheck, lint, and the full test suite.
- Reproduce the P-002 shape in a fixture and prove that legacy cleanup refuses while changes are present, then succeeds after those changes are intentionally handled and integration is proven.

## Constraints

Honor `git.base_branch` and existing protected-branch rules. Treat Git ancestry and the actual worktree state as authoritative at execution time. All canonical `.a-team` mutations must go through supported writers. Cleanup must be opt-in after integration, transactional where possible, fail closed on ambiguity, and never risk user changes or unmerged commits.

## Open decisions

None.

Source: F-003. The current repository is intentionally left untouched on `coord/P-002` because it contains uncommitted P-003 workspace changes. Implement and test the lifecycle fix in an isolated ticket worktree; do not use the current dirty checkout as a cleanup experiment.
