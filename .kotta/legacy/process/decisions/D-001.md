# D-001 — Intake is branch-independent; UI derives state from named refs, never the working-tree HEAD

## Decision

The UI/read layer derives entity state from **named git refs chosen deliberately**, never from the primary working tree's momentary HEAD:

- **baseline** = the configured base ref (`config.yaml` → `git.base_branch`), read via git plumbing *without* checkout;
- **overlay** = active worktrees, shown as in-flight with claim/branch/worktree provenance (UX-SPEC §7);
- disagreement between the two is surfaced as **drift**, never silently resolved.

**Intake (findings) is branch-independent.** Finding writes land in one canonical home, not on whatever code branch happens to be checked out:

- now: commit findings to the **base ref**, serialized by the mutation lock (T-002);
- at scale (external / MCP sources): promote intake to a dedicated, **non-protected inbox ref** (e.g. `a-team/inbox`), decoupling intake volume + write concurrency from the protected base.

Findings are **decoupled** from code work; tickets/packages remain **coupled** (their status derives from the workflow/worktrees). Do not collapse the two.

External sources (user feedback, crash tools, and the MCP servers we will build with bug-report tools) feed the **same** intake through one workspace-addressable create-finding endpoint (A-Team exposed as an MCP server); individual MCPs forward to it rather than each shipping bespoke bug-report plumbing.

## Context

Discovered while dogfooding the one&a workspace (2026-07-26): findings appeared to vanish and reappear from the UI (see F-006). Root cause: the UI reads `.a-team/` from the primary working tree, which is used as a shared branch-switching surface (constant `git checkout main` / `reset --hard origin/main` / `checkout -b` in the main dir). The same instability corrupted a live analysis in this session (reported "0 native findings, 61 backlog / 4 done"; clean counts from `main` are 6+1 native F- findings, 65 backlog / 7 done). This violates the product's foundational *truth from derivation* principle (UX-SPEC §2, §7).

A related design conversation reframed the intake model: intake is a **multi-source** layer (agents during review/impl, human notes, crash tools, and forthcoming MCP bug-report tools) that dedups/clusters; the executable layer ("task") is what is handed to the machine; a "goal" groups tasks toward an outcome.

## Consequences

- **F-006** now has a defined fix direction (read: base + worktree overlay via plumbing; write: intake → canonical ref) and should become a ticket.
- Reinforces **T-002** (shared mutation lock): direct-to-base intake writes require serialization.
- Implies a new backend surface: a workspace-addressable create-finding endpoint + A-Team-as-MCP. Design the **seam** now; **defer** the clustering / dedup / feedback machinery until MCP/multi-source volume justifies it (build-when-it-hurts).
- **Still open (parked, not decided):** the `signal/ticket → task → goal` terminology (3 levels); whether the decision unit is a per-item finding or a cluster/issue; the feedback-to-reporter loop; and **F-005** detail-view design (rank ticket > package > finding by real usage).
